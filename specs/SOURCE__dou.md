# Спека адаптера: DOU (jobs.dou.ua)

> Розвідка: researcher `2cb8da5a`, 27.07.2026. Усе нижче ПЕРЕВІРЕНО живими запитами.
> Вердикт: 🟢 **легко** · ціна підключення ~1–2 год.

## 1. Спосіб доступу

**RSS 2.0.** Ніякого API-ключа, авторизації, Cloudflare. Звичайний GET.

```
GET https://jobs.dou.ua/vacancies/feeds/?category=Design
```

| | |
|---|---|
| Метод | `GET` |
| Обов'язкові заголовки | **немає** (працює навіть без User-Agent) |
| Відповідь | `application/rss+xml; charset=utf-8`, HTTP 200 |
| Розмір | ~150 КБ (з категорією) / ~340 КБ (без) |

Підтверджено: старий зріз від 15.07 **актуальний**, DOU не переїхав удруге. Блокера №1 немає.

### Реальний фрагмент відповіді (обрізаний, з бойового запиту 27.07.2026)

```xml
<?xml version="1.0" encoding="utf-8"?>
<rss version="2.0" xmlns:atom="http://www.w3.org/2005/Atom"><channel>
<title>Вакансії на DOU.ua</title>
<link>https://jobs.dou.ua/vacancies/?utm_source=jobsrss</link>
<description/>
<atom:link href="https://jobs.dou.ua/vacancies/feeds/" rel="self"/>
<language>uk</language>
<lastBuildDate>Mon, 27 Jul 2026 11:59:34 +0300</lastBuildDate>
<item>
  <title>Product Designer (strong UI skills) в Zeely AI, Київ, Варшава (Польща), віддалено</title>
  <link>https://jobs.dou.ua/companies/zeely-ai/vacancies/367245/?utm_source=jobsrss</link>
  <description>&lt;h3&gt;&lt;b&gt;Join ...&lt;/b&gt;&lt;/h3&gt;&lt;p&gt;...&lt;/p&gt;</description>
  <pubDate>Mon, 27 Jul 2026 11:59:34 +0300</pubDate>
  <guid>https://jobs.dou.ua/companies/zeely-ai/vacancies/367245/?1785142774</guid>
</item>
...
</channel></rss>
```

**У `<item>` рівно 5 полів:** `title`, `link`, `description`, `pubDate`, `guid`. Перевірено на 50/50 записах. Більше немає нічого.

## 2. Мапа полів → наша схема

| Наше поле | Звідки | Як |
|---|---|---|
| `source` | — | константа `"dou"` |
| `title` | `<title>` | частина ДО останнього ` в ` |
| `company` | `<title>` | перший сегмент ПІСЛЯ ` в ` (до коми) |
| `location` | `<title>` | останні сегменти після коми |
| `url` | `<link>` | прибрати `?utm_source=jobsrss` |
| `tags` | ⚠️ **НЕМАЄ В ДЖЕРЕЛІ** | див. нижче |
| `posted_at` | `<pubDate>` | RFC-2822, парситься `email.utils.parsedate_to_datetime` |

### Чого в джерелі НЕМА (не додумувати)

- **`tags`** — у фіді немає `<category>` взагалі. Єдине, що можна покласти в `tags` чесно — це значення `category`, з яким МИ зробили запит (тобто наш власний ярлик, не дані DOU). Витягувати теги з `description` — це вже здогадки, не контракт.
- **`company` та `location` окремими полями не існують.** Вони склеєні в `<title>` і дістаються тільки парсингом. Це найкрихкіше місце адаптера.
- Немає рівня/грейду, типу зайнятості, зарплати окремим полем.

### Формат `<title>` — розібраний на реальних даних

```
{title} в {company}[, {salary}][, {location(s)}]
```

Заміри на вибірці 75 заголовків:
- роздільник ` в ` присутній у **75/75**;
- заголовків із **двома** ` в ` (тобто неоднозначних) — **0/75**. Але це не гарантія: назва компанії з « в » усе зламає. Використовуй `rsplit(' в ', 1)`, не `split`.
- зарплата всередині заголовка — **4/75**, завжди СЕРЕДНІМ сегментом: `..., $750–1100, віддалено`, `..., до $7000, за кордоном`. Тобто не можна брати «останній сегмент = локація» наївно; спершу відкинь сегмент, що матчить `[$€]|\d+–\d+`.

⚠️ **Пастка з entity.** Заголовки містять **подвійно екрановані** сутності: у сирому XML лежить `&amp;amp;` і `&amp;nbsp;`. Після одного `unescape` отримаєш `&amp;`/`&nbsp;`, а не `&`/пробіл. Потрібно **два проходи** unescape (5/75 заголовків зачеплено). `feedparser` робить один.

## 3. Фільтри на боці джерела

Усі — query-параметри до `/vacancies/feeds/`. **Перевірено, що реально фільтрують:**

| Параметр | Приклад | Статус |
|---|---|---|
| `category` | `?category=Design` | ✅ працює, валідується |
| `search` | `?search=Product+Designer` | ✅ працює |
| `city` | `?city=Київ` (url-encoded) | ✅ працює |
| `remote` | `?remote` або `?remote=1` | ✅ працює — **25/25 результатів справді віддалені** |
| `exp` | `?exp=0-1` \| `1-3` \| `3-5` \| `5plus` | ✅ працює — перетин `0-1` і `5plus` = **0 записів** |
| `page` | `?page=2` | ❌ **ІГНОРУЄТЬСЯ** (див. §4) |
| `company` | `?company=fuib` | ❌ **ІГНОРУЄТЬСЯ МОВЧКИ** — віддає повний нефільтрований фід |

### ✅ ВИПРАВЛЕННЯ (28.07): per-company RSS усе ж існує

У першій редакції цієї спеки я написав, що фіда по компанії немає — бо пробував `/companies/<slug>/vacancies/feeds/` (404) і `?company=<slug>` (ігнорується). **Обидва шляхи хибні, але сам фід є**, просто за іншим URL:

```
https://jobs.dou.ua/vacancies/<company-slug>/feeds/
```

Посилання «RSS» стоїть прямо на сторінці компанії. Перевірено — віддає рівно вакансії цієї компанії:

| слаг | HTTP | записів | сторонніх компаній |
|---|---|---|---|
| `epam-systems` | 200 | 10 | 0 |
| `mono` | 200 | 7 | 0 |
| `fuib` | 200 | 3 | 0 |

⚠️ **Але він теж обрізається на 25** — я спершу вирішив інакше, бо перевірив на трьох малих компаніях, де вакансій менше за ліміт. Контрольний замір на великій це спростував:

| компанія | лічильник на сторінці | віддав RSS |
|---|---|---|
| `ajax-systems` | **33** | **25** |
| `epam-systems` | 10 | 10 |
| `mono` | 7 | 7 |

Тобто правило те саме, що й для решти фільтрованих фідів DOU: **стеля 25, пагінації немає**. Для компаній із <25 вакансіями фід повний, для більших — губить хвіст.

Практична цінність: стежити за конкретною компанією (банк, топ-50) можна одним дешевим фідом **без адаптера під її кар'єрку** — але для компаній із 25+ вакансіями покриття неповне.

### 🔴 Головний footgun: невідомі параметри ігноруються мовчки

`?company=fuib` віддав **HTTP 200 + 50 записів, з яких 0 стосуються fuib**. Тобто помилка в назві параметра не падає — вона тихо підмінює вибірку на «усі вакансії». Адаптер **мусить** санітизувати: дозволений білий список параметрів, усе інше — виняток на етапі конфігу.

Натомість невалідне ЗНАЧЕННЯ валідного параметра поводиться інакше:
- `?category=NotAReal` → HTTP 200, **0 записів** (не помилка!);
- `?exp=bogus` → HTTP 200, 0 записів;
- `?category=Дизайн` (кирилиця) → **HTTP 400**.

Отже «0 записів» — легітимна відповідь і НЕ мусить вважатись збоєм, але й не мусить мовчки вважатись «нічого нового». Потрібен алерт, якщо категорія віддає 0 кілька циклів поспіль.

Релевантні нам: **`Design`**, **`Product Manager`**. Дотично: `Analyst`, `Project Manager`, `Animator`, `Artist`.

### ⚠️ `category=Design` ≠ UX/UI

Реальний зміст фіду `Design` (25 записів, 27.07): серед них **5 інженерів-конструкторів** — `Інженер-конструктор в НВП "Атлон Авіа"`, `Інженер-технолог (композити)`, `Mechanical Design Engineer`, `Electronics Design Engineer`, `Principal Electronics Design Engineer`. Тобто ~20% сміття для нашої цілі.

Фільтр на боці DOU відсіює дешево, але **не точно**. Клієнтський стоп-лист обов'язковий, мінімум: `інженер-конструктор`, `mechanical`, `electronics`, `композит`, `радіотехнік`.

## 4. Пагінація — ЇЇ НЕМА

Перевірено жорстко, порівнянням ID: `?category=Design` і `?category=Design&page=2` віддають **побайтово той самий набір із 25 ID**.

Ліміти фіду:
- **без фільтра — 50 записів**;
- **з будь-яким фільтром — 25 записів**.

Дістати глибше через RSS **неможливо**. Це не «стоп на N сторінці» — це стеля.

## 5. 🔴 Стабільний ID і чому це впливає на РОЗКЛАД

### Ключ дедупу

`<guid>` виглядає так: `https://jobs.dou.ua/companies/calma/vacancies/367109/?1785142600`

Суфікс після `?` — це **unix-час, рівний `pubDate`**. Я перевірив стабільність: два запити з інтервалом ~7 хв дали **25/25 однакових guid** для тих самих вакансій. Тобто в межах спостереження guid стабільний.

**Але рекомендую ключем брати не guid, а числовий ID з URL** — `367109`, регуляркою `/vacancies/(\d+)/`:
- guid містить час, а DOU **піднімає** (republish) вакансії — при піднятті `pubDate` зміниться, а з ним і guid, і та сама вакансія прилетить у Telegram удруге;
- я **не зміг це підтвердити чи спростувати за одну сесію** (потрібне спостереження ≥доба). Тому це ризик, а не факт. Числовий ID від цього ризику захищає безкоштовно — беремо його.

### 🔴 Розклад: щогодини — на межі, і тільки завдяки фільтру

Заміри охоплення фіду за часом (27.07, ~12:00):

| Фід | Записів | Часовий проміжок |
|---|---|---|
| **без фільтра** | 50 | **1 год 14 хв** |
| `category=Design` | 25 | **4 доби 18 год** |
| `category=Product Manager` | 25 | **4 доби 22 год** |

Висновок, важливий для архітектури: **нефільтрований фід не можна опитувати раз на годину** — він покриває лише ~74 хвилини, запас 14 хвилин, і в піковий день вакансії просто загубляться назавжди (пагінації нема, догнати нічим).

**Категорійний фід опитувати щогодини абсолютно безпечно** — запас ~×115. Тобто фільтр на боці джерела тут не «дешевше», а **умова, без якої розклад втрачає дані**. Якщо колись захочеться «ловити все» — доведеться або дробити на ~10 категорійних фідів, або зменшувати інтервал до ~15 хв.

## 6. Ризики

| Ризик | Оцінка |
|---|---|
| Rate-limit | не спостерігав. ~15 запитів поспіль без затримки — жодного 429. При 2–3 фідах щогодини питання не стоїть. |
| Анти-бот / Cloudflare | **немає.** Голий curl без User-Agent проходить. |
| Playwright | **не потрібен.** |
| Крихкість | **середня, і вся в парсингу `<title>`.** Розмітка фіду стабільна (RSS 2.0), редизайн сайту її не зачепить. Але company/location живуть у рядку заголовка — зміна формату заголовка зламає їх мовчки, з валідним RSS на виході. |
| Мовчазна деградація | найнебезпечніше: і «невідомий параметр», і «нема збігів», і «зламаний парсинг заголовка» дають HTTP 200 і не падають. Потрібні перевірки на боці адаптера, а не надія на виняток. |

**Мінімальні health-check'и, які варто зашити:** (1) кожен запит — тільки з білого списку параметрів; (2) якщо `parse_title` не знайшов ` в ` — не викидати запис, а віддати `company=None` і залогувати; (3) якщо категорія віддала 0 записів N циклів поспіль — алерт.

## 7. Вердикт

🟢 **Легко. Це ядро — підключати першим.**

- Ціна: ~1–2 год на адаптер (з них ~час на парсер заголовка й тести).
- Залежності: `feedparser` (або `xml.etree` + `email.utils` — вистачить stdlib) + два проходи `html.unescape`.
- Дає найбільший обсяг релевантних вакансій за найменші гроші. Оцінка з попередньої сесії («80% цінності дешево») **підтверджується**.
