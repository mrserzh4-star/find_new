# find_new — свої вакансії, зібрані в одну сторінку

Раз на годину сервіс забирає свіжі вакансії з джерел, лишає тільки ті, що
підходять під твої критерії, відкидає вже показані — і перемальовує локальну
сторінку `digest.html`. Нове з останнього запуску підсвічене зверху.

Ніякого сервера, акаунтів і хмари: усе крутиться на цьому ПК.

---

## Як змінити, які вакансії ловимо

Відкрий `config/filter.toml` у Блокноті. Там три списки:

1. **`include_any`** — ловимо вакансію, якщо в назві є хоч одне з цих слів.
2. **`exclude_any`** — не ловимо, якщо є хоч одне з цих (сильніше за перший список).
3. **`[[sources.dou.feeds]]`** — звідки беремо; додати джерело = дописати такий блок.

Зберегти файл — і все. Наступний запуск уже працює по-новому, а вакансії, що
більше не підходять, самі зникнуть зі сторінки. Перевірити, не чекаючи години:

```
python run.py preview
```

покаже, що пройшло б фільтр і що відсіялось — з причиною для кожної.

### Якщо у стрічці зʼявилось не те

**Симптом:** приходять ролі, яких там бути не має — менеджери, інженери,
продавці, — при цьому цифри прогону виглядають нормально і жодної помилки
немає. Це найтихіший спосіб зламатись, бо ніщо не падає.

**Причина зазвичай одна:** біля джерела в конфізі стоїть `trust_category = true`,
а джерело перестало точно розкладати вакансії по категоріях. Прапорець
означає не «у джерела є категорія Дизайн» (вона є в усіх), а «його категорії
достатньо точні, щоб не перевіряти вміст». Це твердження з датою — поруч у
конфізі записано, коли й на чому його міряли. Постав такому джерелу `false`:
тоді знову вмикається перевірка за ключовими словами.

## Бронювання від мобілізації

Сервіс читає текст вакансії й ставить зелену позначку **🛡 є бронювання** там,
де про це прямо написано, разом із цитатою з оголошення — щоб не відкривати
вакансію заради перевірки. На сторінці є перемикач «з бронню» з лічильником.

**Відсутність позначки означає «в оголошенні про це не сказано», а не «броні
немає».** Багато компаній бронюють і просто не пишуть про це.

Формулювання правляться в секції `[reservation]` того ж конфіга. Там же
перемикач `required`: за замовчуванням `false` — вакансії показуються всі,
просто позначені. Вмикати `true` варто лише свідомо: бронювання дають
переважно оборонні й виробничі підприємства, тож на дизайнерських ролях таких
вакансій одиниці, і жорсткий фільтр зробить стрічку майже порожньою.

## Запуск

```
run.bat            один прогін зараз
schedule.bat       поставити щогодинний запуск (запустити один раз)
```

Зняти розклад: `schtasks /delete /tn "find_new hourly" /f`

Результат — `digest.html` у цій же папці. Відкрий у браузері, натисни зірочку
в адресному рядку, щоб не шукати щоразу.

### Команди для перевірки

| Команда | Що робить |
|---|---|
| `python run.py run` | прогін: зібрати, відфільтрувати, оновити сторінку |
| `python run.py run --dry-run` | те саме, але нічого не зберігає |
| `python run.py preview` | що пройшло фільтр і що відсіялось (із причинами) |
| `python run.py stats` | скільки вакансій уже в памʼяті |
| `python tests/test_parsing.py` | перевірка розбору й фільтрів, мережа не потрібна |

## Перший запуск

Потрібен Python 3.11 або новіший.

```
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
run.bat
```

**У перші години частина карток буде без назви компанії.** Це нормально, а не
помилка: на Djinni компанія лежить не у списку вакансій, а на сторінці кожної
з них, і сервіс свідомо не ходить туди сотнями запитів за раз. Назви
дозбируються протягом кількох прогонів.

**Перший прогін навмисно не покаже «нових».** Він засіває памʼять поточними
вакансіями — інакше ти б отримав сотню «новинок» на рівному місці. Новизна
чесно рахується з другого запуску. Те саме станеться, якщо базу видалити.

## Як воно влаштоване

```
run.py                CLI
jobfeed/
  models.py           єдина схема вакансії + стабільний id для дедупу
  filters.py          фільтр за конфігом
  reservation.py      ознака «є бронювання» з тексту вакансії
  store.py            SQLite: памʼять про показане, вона ж джерело правди про новизну
  digest.py           HTML-сторінка
  pipeline.py         склейка
  sources/            djinni · dou · happymonday
    jsonld_jobposting.py  спільний парсер schema.org — переважна більшість
                          джоб-бордів віддає вакансії саме в цьому форматі
    feed_params.py        спільний білий список параметрів запиту
  sinks/              куди віддаємо: html, json, консоль
config/filter.toml    єдиний файл, який править власник
tests/                регресійні тести, працюють без мережі
specs/                спеки джерел (розвідка)
```

Дані течуть так: `джерела → єдина схема → фільтр → дедуп → sinks`.
Ядро не знає ні про DOU, ні про HTML — тільки про два інтерфейси, тому нове
джерело чи новий спосіб доставки додається окремим файлом, без правок у ядрі.

**Де лежить памʼять:** `%LOCALAPPDATA%\find_new\state.db` — навмисно ЗА межами
OneDrive. Синхронізація може підхопити базу посеред запису й побити її.
Шлях міняється рядком `db` у конфізі.

### Додати доставку в месенджер

Місце заготовлене: новий клас з методом `emit()` у `jobfeed/sinks/`, рядок
у реєстрі `sinks/__init__.py` і назва в `sinks = [...]` конфіга. Ключі й токени —
тільки з змінних оточення, у код вони не потрапляють. Ядро не міняється.

### Переїзд у хмару

Код host-agnostic: жодних залежностей від того, що це Windows. Для GitHub
Actions достатньо cron-воркфлоу з `python run.py run` — але тоді стан треба
класти туди, що переживає воркер (комітити базу в репо або взяти зовнішнє
сховище), бо раннер щоразу чистий.

## Твої позначки: «відгукнувся» і «не цікавить»

Під кожною вакансією дві кнопки. «Відгукнувся» лишає картку на видноті й
позначає зеленим. «Не цікавить» — прибирає її зі стрічки (за замовчуванням
такі сховані, перемикач угорі повертає їх).

Позначки переживають щогодинне оновлення сторінки: у кожної вакансії
постійний внутрішній номер, тому після перемальовування вони лягають назад
на ті самі картки.

⚠️ **Але живуть вони в браузері, а не в проєкті.** Це означає:
очищення даних браузера їх зітре, на іншому компʼютері їх не буде, і в
резервну копію проєкту вони не потрапляють.

Тому внизу сторінки є **«Експортувати позначки»** — зберігає файл, який
потім можна повернути кнопкою «Імпортувати». Якщо розмітиш дві сотні
вакансій, зроби копію: відновити це вручну буде довго.

---

## «Ймовірно закриті»

Внизу сторінки є згорнута секція з вакансіями, які джерело перестало
показувати у себе. Найчастіше це означає, що вакансію зняли.

Вони не видаляються і не ховаються назовсім, бо це наш **висновок**, а не
факт: жодне джерело не повідомляє «вакансію закрито». Сервіс лише помічає,
що вакансія зникла з переліку двічі поспіль — і то лише тоді, коли впевнений,
що переліком її не обрізало. Якщо вона повернеться, позначка зникне сама.

## Джерела

| Джерело | Стан | Чому |
|---|---|---|
| Djinni | ✅ головне | окремі точні категорії, ~160 вакансій, компанія й зарплата зі сторінки |
| HappyMonday | ✅ працює | не IT-борд: агенції, медіа, НУО. Перетин роботодавців із DOU — 2 з 19 |
| DOU | ✅ працює | RSS, стабільний, але одна звалка «Design» — потрібен стоп-лист |
| PUMB | ❌ не робимо | за Cloudflare; його вакансії й так є на DOU |
| Andersen | ⏸ відкладено | API працює, але під профіль підходять 5 з 212, жодної в Україні |
| work.ua, RemoteOK | ❌ відхилені | меблі й одяг замість цифрового дизайну / дані-сміття |

Деталі й заміри — у `specs/`.

**Важливо про DOU:** використовуємо лише категорійні фіди. Загальний фід тримає
близько години вакансій — при щогодинному запуску частина губилась би назавжди.
Сервіс не дасть запуститись із незвуженим фідом.
